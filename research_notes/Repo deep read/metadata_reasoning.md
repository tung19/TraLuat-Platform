# Metadata & Data-Type Schemas for Reasoning/Inference — Reference Repos vs. TraLuat

Scope: the concrete METADATA and DATA-TYPE schemas that feed REASONING/INFERENCE in three reference repos — applicability conditions, knowledge-graph node/edge attributes, verification states, and finding structures. Field names, types, file + line. All paths under `refs/`. Read-only; nothing executed.

Bottom line up front: all three encode rich *structural* and *verification* metadata, but **none carries an effective-date / temporal validity attribute on nodes, edges, rules, or findings**, and **none carries a tenant or jurisdiction tag** on its data objects. Those are the two gaps TraLuat is expected to fill for Vietnamese legal AI (versioned law, effective/expiry dates, per-tenant isolation).

---

## 1. LegalGraphRAG — 4-layer HierarGraph KG schema

A single in-memory graph (`GraphDBManager`) carries four conceptual layers: **fact** (Cases/Laws/Crimes + edges), **rule** (the `judge_dep` / `related_laws` fields on a Law node), **ontology** (Cluster nodes, SIMILAR_TO/BELONGS_TO edges, centrality), and a **feature/query** layer (4 ontology dimensions used to build the embedding query). Node/edge attrs are plain Python dicts — no schema enforcement, no typing beyond what each writer sets.

### 1a. Node attributes

**Cases node** — `core/graph_construct/fact_graph.py:31-41` (`store_nodes`), type label `'Cases'`:
- `description` (str), `embedding` (vector/np.array), `caseId` (str), `crime` (list[str] — charge names), `law` (list — article entry numbers the case cites)
- Added later by ontology layer (`ontology_graph.py:117-128`): `communityId` (int), `pagerank` (float), `degree` (float)

**Laws node** — written by `rule_graph.law_node_properties()` at `core/graph_construct/rule_graph.py:9-19`, stored at `fact_graph.py:44-49`, type label `'Laws'`:
- `entry` (int — article number; edges and dedup key off this)
- `description` (str — article text)
- `embedding` (vector)
- `crimes` (list[str] — charge names this article can convict)
- **`judge_dep`** (the constitutive-elements checklist — see 1c)
- **`related_laws`** (judicial interpretations / cross-referenced articles — see 1c)
- `insights` (str, init `''`; mutated in place by `rule_graph.update_insights_in_graph()` at `rule_graph.py:35-37` — the only write-back accumulation slot)

**Crimes node** — `fact_graph.py:52-60`, type label `'Crimes'`: `description` (str — charge name), `embedding` (vector). No other attributes.

**Cluster node** — `ontology_graph.py:202-211`, type label `'Cluster'`: `summary` (str, LLM-generated), `embedding` (vector of the summary), `top_crimes` (list[str]), `top_crime_counts` (list[int]). Created per detected community.

### 1b. Edge types / attributes — `fact_graph.py`, `ontology_graph.py`

- `RELATES_TO_LAW` (Case → Law), no attributes — `fact_graph.py:85`. Built by matching `case.law` entry number to `Laws.entry` (`fact_graph.py:83-87`).
- `RELATED_CRIME` (Law → Crime), attribute **`match_type`** ∈ {`'exact'`, `'fuzzy'`} — `fact_graph.py:121` (exact) / `:131` (fuzzy, substring containment). This is the only edge carrying a provenance/confidence-ish attribute.
- `SIMILAR_TO` (Case ↔ Case), attribute **`score`** (float cosine similarity) — `ontology_graph.py:107`. kNN top-3.
- `BELONGS_TO` (Case → Cluster), no attributes — `ontology_graph.py:216`.

Note: `fact_graph.py:134-155` deletes all Law nodes with `entry <= 101` (general-provisions articles of the PRC Criminal Law) after edge-building — a hard-coded jurisdiction/statute assumption baked into graph construction, no config.

### 1c. `judge_dep` and `related_laws` — the applicability-condition metadata (core of verify_article)

This is LegalGraphRAG's "applicability conditions" mechanism. Produced offline by `scripts/prepare_law_judge_dep.py`, stored as JSON on each Law node, consumed by `core/judge/judge_law.py`.

**Production shape** — `prepare_law_judge_dep.py:275-282` writes rows of:
```
{ "id": <int law_id>, "law": <str article text>,
  "related": [ {"id": <str>, "text": <str>} ],   # judicial interpretations + cross-refs
  "judge":   [ <str>, ... ] }                     # the checklist
```
- **`judge`** = `judge_dep` = a list of **constitutive-element sub-judgments**, each a Chinese string that must start with "是否" ("whether…"). Generated by `JUDGE_PROMPT` (`prepare_law_judge_dep.py:13-25`) which decomposes an article into key applicability elements; parsed/filtered by `parse_judge_list()` (`:64-77`, enforces the "是否" prefix). Example form: `["是否…", "是否…"]`. It is a **flat checklist of boolean-intent predicates**, NOT typed conditions — no operator, no value, no effective-date, no jurisdiction.
- **`related`** = `related_laws` = list of `{id, text}` dicts: (a) cross-referenced articles, resolved by parsing Chinese ordinals "第X条" out of the article text (`extract_referenced_law_ids()` `:54-61`, `build_related_laws()` `:122-141`), and (b) judicial explanations matched by `law_id` membership (`:143-155`), keyed `{id: <source/"judicial_explanation">, text: <explain text>}`.

**Storage detail:** on the node, `judge_dep` and `related_laws` are stored as the raw JSON/string; the Researcher re-parses them with `eval()` at `core/agents/researcher.py:65-66` (`law["judge_dep"] = eval(law["judge_dep"])`). So the live runtime type is `list` (judge_dep) and `list[dict]` (related_laws).

**Consumption — `verify_article()` in `core/judge/judge_law.py:4-33`** (the constitutive-elements checker):
- `diagnostic_checklist = article["judge_dep"]` (`:15`), `judicial_interpretations = article["related_laws"]` (`:16`).
- Loops each `diagnostic_item`, prompts the LLM (`JUDGE_LAW_PROMPT`) with `law_item` (= `article["description"]`), `related` (= judicial_interpretations), `element` (= the sub-judgment), `case` → classifies each element into **`satisfied` / `unsatisfied` lists** by presence of "true"/"false" in the response (`:17-27`).
- Final roll-up prompt `JUDGE_LAW_PROMPT0` takes `true_list` + `false_list` and returns a boolean verdict + free-text rationale (`:29-33`). Returns `(bool, str)`. **This is the verification "state" for LegalGraphRAG** — a per-article satisfied/unsatisfied element partition plus an overall true/false. No persisted enum, no confidence score, no timestamp.

### 1d. Retrieved-law record — what traversal returns for inference

`rule_graph.retrieved_law_record()` (`rule_graph.py:22-32`), returned by `fact_graph.laws_for_case()` (`:158-167`):
```
{ id, entry, description, crimes, judge_dep, related_laws, insights }
```
`feature_graph.retrieve_evidence()` emits the slimmer retrieved-law dict with `{id, entry, description, crimes, judge_dep, related_laws}` (`feature_graph.py:99-107` and `:125-133`). `charge_anchored_articles()` adds `crime_similarity` (float) and `rank` (int) to the same record (`fact_graph.py:231-247`).

### 1e. Charge-prediction labels + structured judgment

- **Charge-anchored retrieval** (`agents/researcher.py:22-35`, `charge_anchored_retrieval`): LLM predicts a **list of charge-name strings** from the fact text (`RETRIEVE_LAW_PROMPT`), parsed as a Python list; each charge string is embedded and matched to Crime nodes (`fact_graph.charge_anchored_articles` `:193-249`). Charge labels are **free-text strings**, not a closed enum.
- **`judge_crime()`** (`core/judge/judge_crime.py:22-39`): returns a deduped `list[str]` of charge names, fallback `["无罪"]` ("not guilty") on parse failure.
- **`synthesize_judgment()`** (`judge_crime.py:41-56`) — the structured output/finding:
  ```
  { "charge_name": <str>,
    "law_article": <str>,
    "term_of_imprisonment": { "death_penalty": bool,
                              "imprisonment": <int, months/years>,
                              "life_imprisonment": bool } }
  ```
  Fallback on parse error (`:55`): `charge_name="无罪"`, `imprisonment=0`. This is the richest "finding" object in the repo — but still carries no effective-date, no statute-version, no jurisdiction tag.

### 1f. Feature/ontology query layer — the 4 applicability dimensions

`agents/researcher.py:10-19` (`ontology_query_text`) serializes a case into four fixed ontology dimensions used to build the retrieval embedding:
- `defendant_info`, `criminal_acts`, `victim_property_details`, `intent_remorse` (each list[str]). These are the "feature" metadata (set via `get_features`, stored under `cases["feature"]`). They function as structured applicability facets but are embedded into one text blob, not stored as typed node attributes.

## 2. L-MARS — per-claim verification metadata + failure_type taxonomy

Citation-quality / NLI verification layer. All in `lmars/verify_agent.py` and `lmars/faith_search/router.py`. Uses `@dataclass` — these are the most strongly-typed schemas of the three repos.

### 2a. Per-claim record — `ClaimRecord` (`verify_agent.py:109-118`)
```
@dataclass ClaimRecord:
    claim: str
    cited_url: str | None
    cited_snippet: str
    support_level: str   # 6-class enum, see 2c
    failure_type: str    # 7-class enum, see 2d
    severity: str        # {minor, major, critical}
    confidence: float    # [0,1]
    explanation: str
```
Serialized form truncates `cited_snippet` to 400 chars (`:153`) and `explanation` to 500 (`:608`). "resolved citation" = `cited_url_resolved` computed in `check_entailment` (`:560-562`) from the matched evidence entry's `url`/`link` — the cited source is located inside the retrieved evidence pool by `_find_cited_evidence()` (`:386-421`): strict host+path URL match (`_urls_match` `:331-355`) then snippet token-Jaccard fallback (`_snippet_match` `:366-383`, threshold 0.5, min 50 chars).

### 2b. Per-answer record — `VerifyReport` (`verify_agent.py:121-162`)
```
question, answer, total_claims (int),
supported_claims, partially_supported_claims, unsupported_claims,
citation_unreachable_claims, no_citation_claims, verifier_error_claims (int counts),
results: List[ClaimRecord],
evaluator_model: str, system_model: str
```
Aggregated metrics are pure functions over this (ALCE-strict precision/recall/F1, coverage, failure_type histogram) — `verify_agent.py:845-947`. `failure_type_distribution()` (`:922-935`) is the diagnostic histogram over the 7 failure types.

### 2c. support_level enum — 6 classes (`verify_agent.py:89-96`, `SUPPORT_LEVELS`)
`supported | partially_supported | unsupported | citation_unreachable | no_citation | verifier_error`
- Case assignment: no cite → `no_citation` (conf 1.0, severity major) `:521-532`; cite given but not locatable in evidence → `citation_unreachable` (conf 0.95, severity critical) `:534-550`; cite resolved → LLM NLI judge returns one of the first three `:586-593`.

### 2d. failure_type taxonomy — 7 classes (`verify_agent.py:97-105`, `FAILURE_TYPES`)
`none | partially_relevant | unsupported | fabricated_source | temporally_invalid | no_citation | verifier_error`
- `fabricated_source` is set when a citation was offered but is unreachable in evidence (`:539-549`).
- **`temporally_invalid`** = cited source addresses a different time period / superseded regulation than the claim asserts (defined in `_VERIFY_SYSTEM` prompt `:213-216`). This is the closest any repo comes to temporal reasoning — but it is a *claim-vs-source* judgment, NOT an effective-date attribute stored on any law/node.
- severity enum `SEVERITIES = (minor, major, critical)` `:106`; `minor`=background, `major`=changes substance, `minor/major/critical` defined in `_VERIFY_SYSTEM` `:218-221`.

### 2e. failure_type → re-search router (`faith_search/router.py`)
`FailureTypeRouter.route()` (`router.py:53-79`) maps each failure_type to a `ReSearchPlan` dataclass (`:43-48`: `query: str, strategy: str, rationale: str`), K-budget preserved:
- `fabricated_source` → re-query restricted to authoritative `.gov`/court/federal-register domains (`_AUTH_DOMAINS` `:33-40`, `_fabricated_source` `:83-99`).
- `temporally_invalid` → add date constraint; extracts a year from claim/hint else appends "current 2026" (`_temporally_invalid` `:101-122`).
- `partially_relevant` → expand with missing specific element parsed from verifier explanation (`_partially_relevant` `:124-145`, `_extract_missing_specifics` `:196-216`).
- `unsupported` → reformulate around the evidence gap (`_unsupported` `:147-167`, `_extract_evidence_gap` `:219-228`).
- `none`, `verifier_error`, `no_citation` → no-op (return None) `:66-67`. (Rationale: re-search can't retroactively cite; `router.py` docstring `:60-65`.)

## 3. claude-for-legal — structured finding metadata, practice-profile schema, typed artifact

Prompt-content repo (Claude Code plugins). "Schemas" are specified in SKILL.md / CLAUDE.md markdown templates, not code. Three relevant schemas:

### 3a. Finding block — the deviation finding structure
`commercial-legal/skills/vendor-agreement-review/SKILL.md:117-136` (markdown template, used by all review skills incl. saas-msa-review which overlays it):
```
### [Section X.X]: [Issue name]
**Playbook says:**  [standard position, quoted from the practice-profile CLAUDE.md]
**Contract says:**  > "[exact quote from the contract]"
**Gap:**  [Missing term | Weaker than standard | Weaker than fallback | Non-standard structure | Unacceptable]   (5-value enum, :124)
**Legal risk:**       🔴 Critical | 🟠 High | 🟡 Medium | 🟢 Low        (:126)
**Business friction:** 🔴 Blocks deals | 🟠 Slows deals | 🟡 Confuses customers | 🟢 Invisible   (:127)
**Why it matters:**  [1-2 sentences plain English]
**Proposed redline:** > "[replacement language, paste-ready]"
**If they won't move:** [fallback from CLAUDE.md, or "escalate to [person]"]
```
- **Dual-axis severity** is the defining feature: Legal risk AND Business friction, each on the same 🔴/🟠/🟡/🟢 scale. Canonical scale + "round UP on ambiguity" and **cross-skill severity FLOOR** rule (downstream skill cannot silently demote an upstream severity) defined in `commercial-legal/CLAUDE.md` → "Cross-skill severity floor" / "Dual severity" sections.
- Severity calibration table (what each level *means* / when to assign) `vendor-agreement-review/SKILL.md:139-148`. Severity is always measured *against the playbook*, not absolute (`:148`).
- Liability-cap finding is decomposed into 4 explicit dimensions (direct vs indirect, cap base verbatim, carveout interaction, playbook position per dimension) `:150-160`.

### 3b. Practice-profile / playbook schema — what a `<plugin>/CLAUDE.md` defines
Per repo-root `CLAUDE.md`: each `<plugin>/CLAUDE.md` is a practice-profile TEMPLATE copied by `cold-start-interview` to `~/.claude/plugins/config/claude-for-legal/<plugin>/CLAUDE.md`. Fields (from `commercial-legal/CLAUDE.md` and `corporate-legal/CLAUDE.md`):
- **Company profile:** Entity name, Industry/sector, Stage, **Primary jurisdiction**, Legal team size, Escalation, Practice setting (Solo/Midsize/In-house/Gov). (Jurisdiction here is a *profile-level* string, not a per-record tag on findings/clauses.)
- **Who's using this:** Role ∈ {Lawyer | Non-lawyer with attorney access | Non-lawyer without attorney access}, Attorney contact — drives work-product header choice + consequential-action gating.
- **Available integrations:** table of {Integration, Status ✓/✗, Fallback}.
- **Playbook** (the applicability/position schema): `Active side` ∈ {sales/purchasing/both}; per-side sections, each clause area (Limitation of liability, Indemnification, Data protection, Term/termination, Governing law/venue) defines **Standard position / Acceptable fallbacks / Never accept** (+ for liability: Direct cap, Indirect damages, Acceptable carveouts, Cap base definition). Plus "The one thing" deal-breaker.
- **Escalation matrix:** table {Can approve, Without escalation (threshold), Escalates to, Via} + dollar thresholds + automatic-escalation list.
- **House style:** redline tone, where work product goes, alert destinations.
- **Outputs / guardrails:** work-product header (jurisdiction-conditioned), reviewer-note block schema (Sources / Read / Flagged / Currency / Before relying), source-provenance tag vocabulary (`[Westlaw]`/`[CourtListener]`/`[user provided]`/`[model knowledge — verify]`/`[settled — last confirmed YYYY-MM-DD]`).
- Corporate module profiles (`corporate-legal/CLAUDE.md`): M&A (materiality thresholds, severity scheme, finding template placeholder), Board, Public Company, **Entity Management** — entity table `{Entity name, Type, Jurisdiction, Owner, Ownership %, Status}` and a `compliance-tracker.yaml`.

Key point: jurisdiction is a profile attribute and a reasoning *trigger* ("Jurisdiction recognition" section — detect non-US facts, refuse confident wrong-jurisdiction answers) but is **not a structured per-clause/per-finding field**. Currency/temporal validity is handled by a *behavioral* "Currency trigger" + `currency-watch.md` reference files (e.g. `ai-governance-legal/references/currency-watch.md`), and by the `[settled — last confirmed YYYY-MM-DD]` tag — a provenance timestamp on a citation, NOT an effective-date on a rule.

### 3c. The one typed artifact — `ma-diligence-columns.md` + tabular-review cell schema
Column schema: `corporate-legal/skills/tabular-review/references/ma-diligence-columns.md` (YAML, `:5-125`). Each column:
```
{ id: <stable str>, label: <str>, type: <type enum>, prompt: <str>,
  options: [<str>, ...]   # classify columns only }
```
**Column `type` enum** (`tabular-review/SKILL.md:70-74`): `verbatim | classify | date | duration | currency | number | free`.
- `verbatim` = character-for-character quote; `classify` = one value from a fixed `options` list; `date`; `duration` = number+unit; `currency` = number+currency code; `number`; `free`.
- The verbatim rule (`SKILL.md:78`, `:156-163`): every non-verbatim cell also captures a companion source quote under the same verbatim obligation.

**Per-cell record** (`tabular-review/SKILL.md:150-153`): `{ value, state, quote, location }` (+`notes`).
- `value` = typed answer, null unless `state == answered`.
- **`state` enum**: `answered | not_present | unclear | needs_review` (`SKILL.md:152`; the three "not found" states defined `:80-88` — `not_present` = read & clause absent; `unclear` = present but unclassifiable; `needs_review` = found but needs human judgment).
- `quote` = verbatim supporting text at `location`; mismatch on re-read downgrades the cell to `needs_review` with `notes: quote_mismatch` (`:160`, `:163`, `:179`). `quote_unavailable: <reason>` when source can't be copied (`:160`).

Example M&A columns and their types (`ma-diligence-columns.md`): `counterparty`(verbatim), `agreement_type`(classify, 14 options), `effective_date`(date), `term`(duration), `auto_renewal`(classify: none/annual/fixed_period/evergreen), `change_of_control`(classify, 6 options), `assignment`(classify, 6 options), `liability_cap`(currency), `governing_law`(verbatim), `confidentiality_term`(duration), etc. Note `effective_date` exists here as a *contract* data point to extract — not as a validity window on a rule/node.

## Gaps TraLuat is expected to fill (absences confirmed across all three)

1. **No effective-date / temporal validity on nodes, edges, or rules.** LegalGraphRAG Law nodes have `entry, description, judge_dep, related_laws` but NO `effective_from` / `expiry` / `version` (`rule_graph.py:9-19`) — the graph is a single snapshot, and it even hard-deletes articles ≤101 unconditionally (`fact_graph.py:134-155`). L-MARS has a `temporally_invalid` *judgment* and a date-constraint re-search, but stores no date on any law object (`verify_agent.py`, `router.py:101-122`). claude-for-legal handles currency *behaviorally* (currency-watch.md, `[settled — last confirmed DATE]` provenance tag, "Currency trigger") — a reminder to re-check, not a structured validity window. For Vietnamese law (frequent amendment, articles with explicit hiệu lực / effective & expiry dates, superseding documents), TraLuat needs effective-date/version attributes as first-class node+edge fields and point-in-time ("as-of date") query — none of the three models this.
2. **No tenant isolation tag.** None of the three carries a `tenant_id` / org-scoping attribute on any data object. LegalGraphRAG is a single global in-memory graph; L-MARS records are per-request; claude-for-legal isolates only by on-disk "matter workspace" folders (`matters/<slug>/`, `commercial-legal/CLAUDE.md` Matter workspaces section) — a filesystem convention, not a data-model tenant tag.
3. **No structured jurisdiction tag on data.** Jurisdiction is a hard-coded assumption (LegalGraphRAG = PRC Criminal Law, baked into the ≤101 delete), a claim-vs-source concern (L-MARS authoritative-domain list is US `.gov`/federal `:33-40`), or a profile-level string + behavioral trigger (claude-for-legal). None attaches a jurisdiction field to a node/edge/finding so results can be filtered or scoped per jurisdiction. For a Vietnam-specific engine with national vs. provincial/ministerial instruments, TraLuat needs jurisdiction/issuing-body as a queryable per-record attribute.
4. **Applicability conditions are untyped.** LegalGraphRAG's `judge_dep` is the only explicit applicability mechanism and it is a flat list of natural-language "是否…" predicates with no operator/value/temporal structure — adequate for LLM-prompted element checking, not for deterministic condition evaluation. TraLuat's "applicability conditions" are expected to be typed/structured beyond this.
